# UDP排序
重新理解UDP排序的原理，我之前对UDP排序的理解是错误的。
接收方在任何有限时刻，都无法区分"这个包丢了"和"这个包只是还没到"。我一直想要去对UDP接受的包进行一个排序
但是这个想法是错误的，正确想法是：人为的规定一个阈值，超过就丢弃包，对延迟和完整性之间做出平衡。

其实对于UDP处理，可以这样抽象2层
- 第一层（传输层）：收包 → 落位 → 判洞 → 输出有序流，流的每个位置要么是数据包，要么是空包
- 第二层（业务层）：只需顺序消费，永远不必知道底下发生了乱序、等待还是丢弃

也就是排序只需要在第一层实现，第二层直接使用排序后的包，进行业务处理。

## 滑动窗口
可以把滑动窗口看作是一个数组，数组的大小就是窗口大小，数组的元素就是包。
slot[seq_cur] 必然为空（drain 停在第一个空格）。这是"滑窗经过它时只判丢、不交付"的依据
每次接受一个包，就根据seq%n计算槽位，放到数组中。然后触发一个读取通知，业务层就可以从数组中读取包，进行业务处理。

那么如何处理UDP的乱？
依据当前已经接受到的seq和接受的包的seq，放到对应的数组中的槽位，
这样遇到当接受的包的seq大于当前数组的长度时如何处理。
这里一个例子
一个长度为5的数组，当前已经接受到的seq是102，103，104，105，期望101
然后接受到了seq是106的包，如何处理，因为如果存放106已经超出了数组的长度。

这是简单的示意图
```
收到 seq
  ↓
更新 highest_seen = max(highest_seen, seq)
  ↓
while highest_seen - seq_cur >= N:     ← 先滑窗，腾位置
    宣告 seq_cur 丢失（实时：PLC / 可靠：NACK）
    slot[seq_cur % N] = None            ← 保险，本来也是空的
    seq_cur += 1
    drain()                             ← 关键，见下
  ↓
slot[seq % N] = (seq, payload)          ← 现在一定装得下
  ↓
drain()
```

### 为什么drain很重要？
因为这是一个主动通知函数，如果不通知 可能会导致已接收的包，没有被业务层处理。
比如接受到106，106-101=5，在滑动过程中，102~104的包就丢失了
