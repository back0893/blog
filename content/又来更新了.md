# kratos v2 学习记录
新工作，需要使用kratos v2，所以需要学习一下。记录一下其中的内容(v2的文档官方就删除，虽然是v3了，但是v2的文档别删，归档也行阿)

## 目录结构
1. api 保存proto 文件，其自动生成的对应的代码在api目录下 api相当于是定义api结构
2. cmd 服务器的入口位置，包含服务的启动逻辑和区分不同的服务 其中使用wire来注入依赖
3. internal 服务的实现逻辑 其中有biz，data,server,service等目录 可以理解为mvc的更多层的抽象
4. config 配置目录 服务的端口，数据库连接信息等都在其中

## 如何添加新的入口定义
```
syntax = "proto3";

package api.helloworld.v1;
import "google/api/annotations.proto";

option go_package="helloworld/api/helloworld/v1;v1";

service HelloWorld{
    rpc SyaHi(SayHiRequest)returns(SayHiResponse){
        option (google.api.http)={
            get: "/hello/{name}"
        };
    }
}
message SayHiRequest{
    string name=1;
}
message SayHiResponse{
    string message=1;
}
```
除开go_package这行，其他都是标准的proto语法，不用过多解释
只有go_package这行需要说明 这是编译后的go代码的包名，其中[name1]:[name2] 是代码不同的包名称
其中的name1表示的是编译后的server中引用的包名，name2表示的是编译后的go代码的包位置的名称
后续还添加了一个http的路由定义，这样proto生成的代码时就也会去生成http的代码

还有一点需要注意，grpc或者http只是定义并生成，不代表其已经实现和注册，注册就是类似http的路由注册，这需要手动去添加

## wire 注入依赖
理解wire注入依赖和步骤
1. 定义依赖提供函数，这一步是用来声明，哪些函数是用来提供依赖
2. 集合，所有的提供依赖函数集合，因为不同的抽象层会提供不同的依赖集合
3. 注入，这一步就是用来依据依赖声明，来注入依赖的，通过创建代码文件来实现

## wire是实现注入依赖？
理解这个非常重要，因为kratos框架中，所有的服务都是通过wire来注入依赖的，不理解就无法理解注入依赖的机制
wire的生成规则：依赖提供构造函数的签名来实现的，会依据函数签名推倒，入参为声明的依赖，出参为出产的依赖(可以为其他依赖)
这样一个例子：
```
以 demo 的 *event.Event 为根，wire 这样回溯：
1. 要 Event ⟶ 用 NewEvent，它的依赖是 *greeter.Greeter
2. 要 Greeter ⟶ 用 NewGreeter，它的依赖是 *message.Message
3. 要 Message ⟶ 用 NewMessage，它的依赖是 *conf.MessageConfig
MessageConfig 正好是入口函数 initApp(cfg) 的参数（种子），终止
```
还有一点就是`wire.Build`的调用方就是需要生成的函数，其入参和出参就是依赖的声明和产出

## 添加新的服务器流程
1. 定义proto文件，其中会有service和message，`kratos proto client`和`kratos proto server -t internal/service` 分别会生成对应的pb代码和接口定义
2. 为data，biz，service,server等层添加对应的实现代码，别忘记了为wire 提供构造函数
3. 在cmd目录下的入口，修改wire的集合，添加新的依赖提供函数,最后重新生成wire生成的代码文件
对的 实现起来起来是这样 proto的实现和编译记住命令 就可以了
然后就是各个层的实现和为wire提供构造函数集合，然后重新使用wire注入依赖
ps: v2版本定义proto时，不要以service结束，使用kratos 生成server代码时，会自动去掉结尾的service

## 最后
kratos的调用流程，其实和其他框架差不多，不走注册中心就是ip注册，然后grpc客户端调用，然后grpc本身对外可以提供http路由
那么大部分时候，gateway负责全部的对外暴露，然后内部在service负责组织调用biz层的逻辑
biz层负责处理业务逻辑，然后调用data层的逻辑
data层负责处理数据库的逻辑
这样一个分工流程，其实和mvc的分层架构是一致的，内部调用看成http也行，框架的流程和原理不难理解
